# Legends of Wand & Sword · 杖剑传说

服务端权威的 Web 放置手游（Playable 原型）：Go 单二进制权威服务 + 原生 Canvas 部件动画前端，单端口同源部署，支持多端接入。

当前最新归档版本：**v1.9.44**（历史归档分支保留，按需拉取）。

## 快速开始

```bash
cd server && go build -o ../data/zjcs-server .
cd .. && ./data/zjcs-server -addr :3000 -config configs -web web/index.html -res web/res
# 打开 http://localhost:3000
```

资源需从 `assets/v1.9.44` 回填到 `web/res/`，映射表见 assets 分支的 `README.md`。

## 技术概览

- **服务端**：Go，单二进制，HTTP + WebSocket，存档落 JSON；战斗/掉落/宝箱/装备/仓库/副本全部服务端权威
- **前端**：原生 JS + Canvas，部件化骨骼动画（parts/actions 配置驱动），单通道 UI 状态机
- **大世界**：6 个 15360×8640 世界，地形图 + 通行掩码硬碰撞；渲染按 1280×720 分块纹理 + 异步裁剪 + LRU，规避 GPU 纹理上限
- **多人**：WS 10Hz 快照，`worldId+channel` 分线（40 人/线），断线退避重连

> **Part A · 已上线实际版本**——从 `code/v1.9.44` 分支配置逐字段实测提取（含每个职业倍率、每个技能 CD/威力、每个怪物基础值、每个世界点位坐标）；

> **数值纪律**：配置表里的值均可在 `configs/*.json` 改，但除标注「设计决策 / 已核实」外，其余为 **[PLACEHOLDER]**——未经 playtest 经济闭环验证，不作最终手感。改配置后服务端重启或热重载生效，不改代码。

## Part A · 已上线实际版本（code/v1.9.44 实测）

### A1. 产品定位、技术栈与运行形态

| 维度 | 实际实现 |
|---|---|
| 一句话定位 | 服务端权威、单端口可部署、多端可接入的放置手游 Playable 原型 |
| 首要平台 | Web（原生 JS + Canvas 部件动画）；另有 Cocos Creator 3.8 客户端骨架 |
| 服务端 | Go 单二进制，standalone HTTP :8080；生产走 Nakama 协议同构（账号/Storage/匹配/实时） |
| 部署 | 单 Go 二进制 + `$PORT` / `0.0.0.0` 单端口，`HandlerWithWeb` 同源托管前端与资源；secret 固定派生 + userId query/body 兜底规避多 worker token 不一致 |
| 通信 | WebSocket/WSS；standalone 同端口 HTTP→WS 升级；公网内测经 Cloudflare/ngrok 隧道自动签发 WSS，不备案不自购证书 |
| 存档 | standalone 落 `data/saves/<userId>.json`（原子写 tmp+rename）；生产对应 Nakama Storage + 关系库 8 张逻辑表 |
| 多人 | Nakama Match(world) 服务端权威坐标 + 限速校验 + 40 人/线；10Hz 快照广播 |
| 渲染性能 | 大世界视口裁剪（±1 屏）+ 分块异步建块 + LRU；部件图 NEAREST 整数倍缩放；目标 60fps |
| 配置驱动 | 6 个 JSON 全部数值外置，服务端与客户端各有同步副本；改配置即改游戏 |

**两种运行模式**：

| 模式 | 启动 | 用途 | 服务端 |
|---|---|---|---|
| standalone（默认，初跑用） | `bash scripts/start.sh` / 双击 `启动初跑.bat` | 立即跑通属性/战斗/离线，浏览器开 `web/index.html` 验证 | Go HTTP :8080 |
| Nakama（联网完整） | `cd server && docker compose up -d` | 账号/Storage/匹配/实时多人；公网配 Cloudflare/ngrok 隧道 | Nakama :7350 |

两模式共用 `internal/game` 权威逻辑，改一次两边生效。Nakama Go 插件需用与 Nakama 相同的 Go 版本、启用 `//go:build nakama` 标签编译为 `.so`。

### A2. 职业系统（classes.json · 逐字段）

**基础属性 baseStats**：HP `100` / ATK `12` / DEF `5` / 暴击 `0.05`（5%）/ 速度 `10`。

**成长公式（v1.9.43 起线性）**：属性(级) = base × `1 + (growth-1)×(lv-1)`，替代旧指数 `growth^(lv-1)`。原因：玩家线性成长（+18血/+3攻/级）vs 怪物指数成长，导致 Lv20 旧甲虫将军 11143 血/604 攻 vs 玩家 552 血（一刀秒）、Lv30 达 58320 血/3159 攻。改后 Boss growth 单独降 `1.08`，高等级单次攻击约为玩家血量 6.1~14%（上限 15%/18%）。

**刷新权重 spawnRule**：普通 `0.7`（70%）/ 精英 `0.25`（25%）/ 稀有精英 `0.05`（5%）；精英 HP×`1.8`、ATK×`1.4`；稀有精英 HP×`2.6`、ATK×`1.8`；保底 pity=`8` 次未出高价值强制出。服务端权威。

**v1.9.42 怪物数值再削**（对照玩家基准 Lv1 战士 120血/12.6攻/5.8防）：史莱姆 70/8→55/6、骷髅兵 114/13→80/9、蝙蝠 84/17→60/11、血蝙蝠 110/22→78/15、甲虫将军 598/36→480/26（v1.9.43 再降至 280/22/6）。

### A6. 经济与全局数值（economy.json · 逐字段）

**离线收益 idle**：

- `maxHours` = 8
- `efficiency` = 1.0
- `expPerMinute` = 6
- `goldPerMinute` = 4
- `materialPerMinute` = 0.5

> 离线收益 = 时长 * 速率 * 效率，封顶8h。结算只用服务端时间戳 lastSeen，客户端改系统时间无效。

**体力 stamina**：

- `max` = 120
- `recoverMinutes` = 30
- `perRecover` = 1
- `costPerBattle` = 0
- `costPerDungeon` = 10

> 挂机/普通交战不消耗体力；副本消耗体力。原型展示值 86/120。

**战斗 battle**：

- `minSeconds` = 15
- `maxSeconds` = 30
- `tickMs` = 1000

> 服务端按累计时间驱动自动战斗；回合数仅作UI展示，不作终止条件。种子由服务端生成随战报记录。

**掉落 drop（以服务端 `server/configs_shared/economy.json` 为准，权威）**：装备掉率 普通 `0.45` / 精英 `0.85` / Boss `0.9`（Boss 掉落循环 `for rng<概率` 加 10 件上限护栏，修复概率=1.0 时的死循环）；Boss 钻石 `50~100`。

**宝箱档位金币/宝石范围（drop.chest）**：

| 档位 tier | 语义名 | 金币范围 | 宝石范围 |
|:--:|---|---|---|
| 1 | wood 木 | 40~120 | 2~8 |
| 2 | silver 银 | 120~300 | 8~20 |
| 3 | gold 金 | 300~800 | 20~50 |
| 4 | diamond 钻 | 600~1200 | 40~80 |
| 5 | crystal 水晶 | 1200~2400 | 90~180 |

> **重要：配置副本不一致（实测）**。服务端权威文件 `server/configs_shared/economy.json` 有全部 5 档；客户端副本 `client/assets/configs/economy.json` 和 `client/assets/resources/configs/economy.json` **只有木/银/金 3 档**——客户端不参与 roll，仅展示用，故不影响权威结算。开箱时 `world.go` 读的是 `game.C().Economy.Drop["chest"]`（服务端加载 `configs/`，部署时须指向含 5 档的那份），按 tierName 取档，取不到回退 wood。

**开箱收益计算（`world.go chestOpen`，逐字段对齐代码）**：

| 收益项 | 计算方式 | 代码依据 |
|---|---|---|
| 金币 gold | 档位 gold 区间 `rand.Intn(hi-lo+1)` 均匀 roll | `rg("gold")` |
| 宝石 gem | 档位 gem 区间均匀 roll | `rg("gem")` |

### A9. 通信协议与存档分表

**协议信封**：`{ "type": "...", "seq": 7, "v": 1, "data": {...} }`；错误带 `code` + `msg`；协议版本 `v=1` 向前兼容。

| 方向 | type | 主要字段 | 说明 |
|---|---|---|---|
| C→S | login | deviceId / username+password | 设备登录或账密 |
| C→S | submit_bd | slots[4] | 战前技能配置，战斗中不生效 |
| C→S | engage | monsterId、monsterLv、elite、seed | 请求交战，服务端起权威战斗 |
| S→C | battle_report | rounds[]、result、rewards、seed | 战报，客户端只表现 |
| S→C | state_snapshot | level/gold/stamina/lastSeen/坐标 | 登录/重连后权威快照 |
| C→S | claim_idle | — | 请求结算离线收益 |
| C→S | match_req / join | mode、roomId | 实时多人匹配/加入 |
| S→C | player_move | playerId、x、y、ts、action | 位置广播，客户端插值 |
| 双向 | heartbeat / pong | ts | 心跳保活与断线判定 |

**standalone HTTP API**（初跑验证用）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /health | 健康检查（含 persist 字段） |
| GET | /api/config | 全量配置 |
| GET | /api/tables | 分表清单 |
| POST | /api/stats/calc | 属性计算（body: Avatar） |
| POST | /api/character/new | 创角并落盘（body: {userId,name,classId}） |
| POST | /api/state/load | 读档（body: {userId}） |
| POST | /api/battle/resolve | 纯战斗结算，不落库（回放用） |
| POST | /api/battle/fight | 战斗结算 + 奖励入账 + 落库 |
| POST | /api/idle/settle | 纯离线结算，不落库 |
| POST | /api/idle/finalize | 离线结算 + 入账 + 推进 lastSeen + 落库 |
| POST | /api/transfer | 转职 + 装备换算 + 落库 |

**权威原则**：战斗结果、离线收益、随机种子全部服务端生成，客户端下发数值一概不采信；`engage.seed` 仅用于复现（>0 采用，=0 服务端随机）；断线重连以 `state_snapshot` 覆盖本地缓存。

**存档分表（8 张逻辑表）**：角色核心(userId/level/exp/battlePower/classId)、世界进度(userId/mapId/coord/unlocked/lastSeen)、仓库(userId/itemId/qty/slot)、装备(userId/slot/itemId/enhanceLv)、技能(userId/slots[4]/unlocked[])、幻兽(预留无入口)、家园(预留)、日志(埋点战报索引)、扩展位(userId/key/json，新增系统零改表)。

**多人 Match（opCode）**：1=`move`{x,y,ts,action} C→S；2=`snapshot`{players[],tick,worldId} 10Hz S→C；3=`join`；4=`leave`。RPC `join_world`{worldId}→{matchId,worldId}。防作弊 speedOK：位移 >600 单位/秒丢弃，单线上限 40。

## Part B · 设计档案（决策、公式与 rationale）

> 来自设计阶段文档，是实现溯源与判断依据。每个决策遵守「先 fun hypothesis → design pillars → 具体系统」，数值带 rationale 或 [PLACEHOLDER]。

### B1. 核心设计哲学

**Fun hypothesis**：这款放置手游好玩的核心是——**大世界探索的「发现感」（路网里藏着怪和箱）+ 服务端权威战斗的「确定性」（离线也在变强）+ 捏出自己角色的「表达感」**。

**5 条设计支柱**（需求文档表1）：

| 支柱 | 体验标准 | 违反即砍 |
|---|---|---|
| ① 离线也在成长 | 离线期间必须产出核心资源，不为「没在线」受罚 | 离线收益为零、离线被打回退 |
| ② 每次上线有决策 | 单次 session 至少一次有效选择：调技能/换装备/选探索路线 | 上线只有「点领取」一个动作 |
| ③ 转职零成本试错 | 切换职业不损失已投入资源，鼓励反复体验流派 | 转职需重练、装备作废 |
| ④ 横版 XY 自由走位 | 核心循环在横版正俯视可配置分辨率地图完成，遇怪选择后切独立战斗场景 | 锁死一条直线、遇怪无选择、探索战斗挤同屏 |
| ⑤ 变强看得见 | 战力/伤害/资源增长有清晰即时反馈 | 数值静默变化 |

**Core Loop 三层钩子**（需求文档表2）：

| 层级 | 时间 | 动作→反馈→奖励 | 回答的问题 |
|---|---|---|---|
| Moment-to-moment | 0–30s | 正俯视 XY 走动→怪进视野弹「交战/绕行」→选交战切独立战斗场景→回合制跳伤害→结算返回 | 这一步走动在期待什么？（遭遇与选择） |
| Session | 5–15min | 领离线收益→调一次技能/装备→推几张图→打一次副本 | 这次上线完成了什么？（一次成长决策） |
| Long-term | 数天–数周 | 攒够材料→解锁转职→成型新流派→挑战更高关卡 | 明天为什么回来？（下一流派与更高战力天花板） |

两张张力（不假装一致）：①「离线也在成长」vs「横版 XY 自由走位」——走动是可选主动探索层，不是必做日常；若 playtest 显示玩家被迫长时间走动才跟得上成长，需给走动产出加「离线等价物」。②「空间可学习」（点位固定）vs「节奏不可背板」（内容随机）——随机放在时间与内容维度，确定性留在空间维度。

### B5. 地图设计（逐条决策与坐标口径）

**地图核心概念（程序员必读）**：地图是「狭窄通道网络」，不是开阔大世界自由跑。三个可验收特征：① 移动受通道约束（墙是硬碰撞非装饰）；② 决策发生在岔口（路线取舍）；③ 视野受通道限制（走近才 roll 内容）。判断唯一标准：角色能否离开通道任意方向自由跑——能，就是没理解。

**通道性五类型（2.5 节）**：

| 类型 | 宽度 | 怪密度 | 玩家决策 | 地形 |
|---|---:|---|---|---|
| 主干道 | 384px | 低 | 赶路默认选 | 宽直连安全区与通道口 = 角色128px×3 |
| 支路 | 64px | 高 | 绕路刷怪，时间换收益 | 窄弯通向产出点 |
| 环路 | 80px | 中 | 绕开某段/换条路 | 连两条主干的第二路径 |
| 暗道/捷径 | 48px | 中高 | 发现了就赚，需解锁 | 入口不起眼，视野遮挡 |
| 死胡同 | 64px | 尽头高 | 搏精英/宝箱需原路返回 | 单端连通，尽头高价值点 |

**复杂度图论指标**：路网节点 20~26、通道边 28~36、独立环数 E−N+1 **≥6**、死胡同 2~3、暗道 1~2、跨世界通道口 2~3。生成 6 步：骨架→加环（≥3 横向连接）→加岔（2~3 死胡同尽头放高价值）→加暗道（1~2 隐藏捷径）→填点（按 tier，每环路至少 1 收益点）→校验（任意两点≥2 路径、环数≥6、无孤立节点、死胡同尽头必有产出）。示例 W2：20 节点/32 通道/13 独立环/2 死胡同/2 暗道/17 产出点。

**比例锚点（务必按此实现）**：角色 character_size `32` × scaleRoot `4` = 场景显示宽 `128px`（角色创建 v4.1 后逻辑画布改 64×96、scaleRoot 改 2，屏幕显示仍 128×192 不变）；主通道 384px = 128×3（角色=道路 1/3）；世界 15360×8640（设计格 480×270，每格 32px）；移速 960px/s（横穿约 16s）；地图 1 图像像素 = 1 场景单位（1:1 加载不再缩放）；相机视野不变 1280×720。

**地形分块 + 通行掩码（2.6 节）**：单世界切 2×2=4 块，每块 7680×4320；切缝落在中央安全区(x=240)与横向主通道(y=135)，拼缝藏在地形里。每块附同源 `*_mask.png`（白255可走/黑0墙），程序按逻辑坐标拼成 480×270 网格，白色并集即移动可行走区，据此生成碰撞体/NavMesh。W2 实测 100% 单连通、4 块掩码拼接与全图逐像素一致。交付物每世界：4 地形块 + 4 掩码 + full/full_mask + annotated_preview + stitch_config。

**AI 地表重绘（2.7 节）**：6 张主题地表材质图（gpt-image-2 各 1 张 1K），降色到各世界 16 色板地表色系（色号 0-6）作不可走草地底纹；可走区（土路/开阔区/暗道/法阵）按 design 类型叠加辨识色；撞色主题加浅色路沿描边（色号 11）。结构层（design 网格/掩码/384px/尺寸/切缝/stitch）一个字节不动，色数仍 16/16，程序接入方式不变。

**固定点位三轴规则**：位置固定（坐标写死可形成心智地图）+ 时刻随机（冷却 base×(1+U(-jitter,jitter))，服务端常驻推进不依赖玩家在线）+ 内容随机（普通怪点 70%普通/25%精英/5%稀有精英；宝箱点 v1.9.42 代码值 木56%/银28%/金12%/钻2.5%/水晶1.5%，带保底 8；需求早期稿 60/30/10 已被取代）。点位字段：nodeId/worldId/coord/type/tier/state/nextRollTs/scope（WORLD 怪与 GATE，USER 宝箱）。槽状态机：EMPTY→ACTIVE→DEPLETED→EMPTY。

**开阔节点（v0.9 局部破墙大空间）**：通道交汇处/死胡同尽头破墙形成开阔节点，做节奏对比与路线辨识。数量 [PLACEHOLDER · 建议每世界 2~4 处]、尺寸 [建议通道宽 2~3 倍见方]、不刷精英（可放普通怪/宝箱）、视野放大 ±1.5 屏 [PLACEHOLDER]。W4 冰霜高原开阔区偏多为差异化设定。
### B6. 角色创建与换装（逐条决策）

**Fun hypothesis**：让玩家第一分钟捏出「像自己」的角色，之后每次换装/转职都在同一具身体上看见变化。

**4 条支柱**：P1 第一分钟有表达（注册后强制进创建界面）；P2 两套外观各归其位（家园休闲装 vs 装备装按场景切）；P3 转职零成本不丢脸（脸型/休闲装永久保留）；P4 技能 BD 只看可选（按职业过滤）。

**6 槽创建（v4.1）**：脸型 face / 发型 hair / 上衣 top / 裤子 pants / 鞋子 shoes / 帽子 hat，各 4 选项，`4^6 = 4096` 组合。脸=纯脸（光头五官圆/鹅蛋/方/心形）、发=纯发丝（棕短发/黑长直/金短发/红马尾），独立两槽，用同一网格坐标系切分（整格裁+统一缩放到 56 逻辑宽），叠放中心天然对齐。职业开局仅战士/法师 2 个。初始技能：普攻×1 + 2 初始技能（理解为全给，玩家创建时确认非二选一）。

**外观状态机**：家园 Home = `appearance.homeLook`（脸+发+上衣+裤+鞋+帽永久保留）；探索 World / 战斗 Battle = 装备 4 槽 + `appearance.face`（职业整体立绘自带固定发型 + 装备覆盖，face/hair id 保留但不渲染）。战斗态禁止换装。叠放顺序 `face→hair→hat→top→pants→shoes`。

**技能 BD 过滤规则**：技能库 = `unlocked[]` ∩ 当前 `classId` 技能集合；开局只显示 2 个初始技能；进阶后显示初始+高阶；转职后切新职业池、原职业技能自动卸下、不显示跨职业灰技能。

**画布升级（技术裁定）**：逻辑画布 32×48 → **64×96**，scaleRoot 4 → **2**，屏幕显示仍 128×192（人物地图大小与比例锚点不变）。理由：AI 精致像素压 32×48 五官全糊，64×96 保住细节。配套地图文档 character_size/scaleRoot 同步为 64/2。

**v5 风格回退（最新裁定）**：初版 AI 精致像素降 16 色后五官糊、判定太丑 → 回退「第一版法师」大色块像素风（大眼睛圆脸、平涂、硬描边、≤16 色）。实现仍 AI 出图，但提示词约束 chunky solid-color blocks/no anti-aliasing；降采样 NEAREST（旧 LANCZOS 揉糊），量化自适应 MEDIANCUT（旧固定色板颜色对不上）。已实测 7 立绘 + 24 部件全 ≤16 色。

**数据落点**：`appearance.homeLook={face,hair,top,pants,shoes,hat}`（存选项 id 不存图片路径，换素材不改存档）、`classId`、`slots[4]`。

### B7. 程序动画（8 动作逐字段）

**核心结论**：动画 = 一张立绘 + root 变换参数，不是逐帧图。程序读 `actions.json` 关键帧线性插值。

| 能做 | 不能做 |
|---|---|
| 整体位移 dx/dy、旋转 rot（绕脚底锚点）、缩放 sx/sy、闪白 flash、淡出 alpha | 挥剑/抬手等肢体动作、关节弯曲、武器挥舞弧线、面部表情、衣料物理 |

**actions.json 字段**：`t`(ms 关键帧时间)、`dx/dy`(px 基于128×192，默认0)、`rot`(度顺时针为+，默认0)、`sx/sy`(系数默认1.0)、`alpha`(0~1默认1)、`flash`(0~1默认0)、`fps`(插值采样率)、`loop`(bool)、`_rationale`(依据，运行时忽略)。锚点 `foot-center`=立绘底边中点，所有变换绕此点保证脚不飘。

**8 动作**：idle(呼吸 sy 1.0→1.02，循环) / walk(4 步态 dy±3 rot±2，循环) / attack(前冲→回弹→收势，近战前冲14px 法系5px) / cast(蓄力拉伸→释放，法系 sy1.06 近战1.02) / hit(后退+闪白) / death(旋转倒地+淡出) / victory(上跳+拉伸) / celebrate(双跳摇摆，循环)。覆盖 6 职业 × 8 动作，3 处路径已同步（parts_v2/parts/v5交付包）。**命名变更**：原 `die` 统一为 `death`。

**逐帧方案（已取消）**：原规划 180 帧（30 帧/职业×6，约 900–1800 积分）。已生成 5 张 AI 测试图验证策略（法师待机 4 帧 + 攻击 1 帧，归档不进交付），确认 high fidelity 既锁身份又能做大幅动作，但用户裁定「太费钱」改用程序生成，0 积分。逐帧管线备查：抠白→NEAREST 降采样 64×96→自适应 MEDIANCUT 16 色→NEAREST×2 导出 128×192。

**Playtest 失败信号**：A 待机看不出呼吸→加大 sy 到 1.04；B 行走像滑步→加大 dy 到 ±5；C 受击闪白像卡帧→缩短 flash 峰值到 50ms；D 死亡淡出太快→延长末帧到 900ms。
